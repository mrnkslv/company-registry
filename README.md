# Company Registry

A Go microservice for managing companies: create, read, partially update and delete.
Mutating operations are protected with JWT authentication; reading is public.

## Features

- **REST API** on [chi](https://github.com/go-chi/chi) with versioned routes (`/company/v1`, `/auth/v1`)
- **PostgreSQL** storage via [sqlx](https://github.com/jmoiron/sqlx) and the pgx driver
- **Migrations** with [goose](https://github.com/pressly/goose), embedded into the binary and applied automatically on startup
- **JWT authentication** (HS256) for create, patch and delete
- **Partial updates**: `PATCH` changes only the fields that were sent, inside a transaction with `SELECT ... FOR UPDATE`
- **Validation** in the domain layer, duplicated by constraints in the database
- **Consistent error mapping**: domain errors are translated to `400`, `401`, `404`, `409`
- **Swagger UI** generated with [swaggo](https://github.com/swaggo/swag)
- **Configuration from environment variables**, with an optional `.env` file for local runs
- **Structured logging** with [zap](https://github.com/uber-go/zap) and graceful shutdown
- **Docker**: multi-stage build on a distroless image, `docker compose` with a Postgres healthcheck

## Quick start (Docker)

Requirements: Docker with Compose v2.

Compose reads a `.env` file, so create it first (see [Configuration](#configuration) for an example; inside Docker the
database address is overridden by `docker-compose.yml`):

```bash
touch .env
docker compose up --build
```

The service starts on `http://localhost:8080`. Postgres is exposed on `localhost:5434`.

To stop and remove the data volume:

```bash
docker compose down -v
```

## Local run (without Docker for the app)

Requirements: Go 1.27+.

1. Start only the database:

   ```bash
   docker compose up -d db
   ```

2. Create `.env` in the project root:

   ```dotenv
   HTTP_LISTEN_ADDRESS=:8080
   PG_DSN_COMPANY_REGISTRY=postgres://postgres:qwerty@localhost:5434/company_registry?sslmode=disable
   AUTH_SALT="jfghdlkoviojkfdko"
   AUTH_SIGNING_KEY="fhvjiokig98y##6785409396"
   DEBUG=true
   ```

3. Run the service:

   ```bash
   go run ./cmd
   ```

## Configuration

All settings come from environment variables. A `.env` file in the working directory is loaded if present.

| Variable | Required | Default | Description |
|---|---|---|---|
| `HTTP_LISTEN_ADDRESS` | yes | | Address to listen on, e.g. `:8080` |
| `HTTP_READ_TIMEOUT` | no | `15s` | |
| `HTTP_WRITE_TIMEOUT` | no | `15s` | |
| `HTTP_IDLE_TIMEOUT` | no | `60s` | |
| `HTTP_SHUTDOWN_TIMEOUT` | no | `15s` | Graceful shutdown timeout |
| `PG_DSN_COMPANY_REGISTRY` | yes | | Postgres connection string |
| `PG_MAX_OPEN_CONNS` | no | `5` | |
| `PG_MAX_IDLE_CONNS` | no | `5` | |
| `PG_CONN_MAX_LIFETIME` | no | `5m` | |
| `AUTH_SALT` | yes | | Salt for password hashing |
| `AUTH_SIGNING_KEY` | yes | | Secret for signing JWTs |
| `AUTH_TOKEN_TTL` | no | `12h` | Token lifetime |
| `DEBUG` | no | `false` | Debug log level |

The values in `docker-compose.yml` are for local development only. In production, secrets must be provided by the
environment (orchestrator secrets, vault, etc.).

## API

| Method | Path | Auth | Description |
|---|---|---|---|
| `POST` | `/auth/v1/login` | no | Get an access token |
| `GET` | `/company/v1/{id}` | no | Get a company |
| `POST` | `/company/v1/` | yes | Create a company |
| `PATCH` | `/company/v1/{id}` | yes | Update some fields of a company |
| `DELETE` | `/company/v1/{id}` | yes | Delete a company |

Protected endpoints expect the header `Authorization: Bearer <token>`.

### Company

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Generated by the service |
| `name` | string | Required, up to 15 characters, unique |
| `description` | string | Optional, up to 3000 characters |
| `amount_of_employees` | integer | Required, must be positive |
| `registered` | boolean | Required |
| `type` | string | One of `Corporations`, `NonProfit`, `Cooperative`, `Sole Proprietorship` |

### Examples

Get a token. A test user `testusername` is created by the migrations:

```bash
TOKEN=$(curl -s -X POST http://localhost:8080/auth/v1/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"testusername","password":"<password1>"}' | jq -r .token)
```

Create a company:

```bash
curl -i -X POST http://localhost:8080/company/v1/ \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "name": "Acme",
    "description": "Test company",
    "type": "Corporations",
    "amount_of_employees": 10,
    "registered": true
  }'
```

Get it:

```bash
curl -i http://localhost:8080/company/v1/<id>
```

Update some fields:

```bash
curl -i -X PATCH http://localhost:8080/company/v1/<id> \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"amount_of_employees": 25, "registered": false}'
```

Delete it:

```bash
curl -i -X DELETE http://localhost:8080/company/v1/<id> \
  -H "Authorization: Bearer $TOKEN"
```

### Errors

Errors are returned as JSON:

```json
{"code": 404, "type": "Not found", "message": "Object not found"}
```

| Status | When |
|---|---|
| `400` | Malformed JSON, invalid UUID, validation failed |
| `401` | Missing or invalid token, wrong credentials |
| `404` | Company not found |
| `409` | A company with this name already exists |
| `500` | Unexpected error |

## Swagger

When the service is running, Swagger UI is available at
[http://localhost:8080/swagger/index.html](http://localhost:8080/swagger/index.html).

The spec lives in `docs/` and is committed, so the project builds without extra tools. To regenerate it after changing
handler annotations:

```bash
brew install swag   # or: go install github.com/swaggo/swag/cmd/swag@latest
swag init -g main.go -d cmd,internal/application/rest,internal/application/rest/dto -o ./docs --parseInternal
```

Rebuild the Docker image afterwards (`docker compose up --build`), because the spec is compiled into the binary.

## Project structure

```text
cmd/                         entry point
internal/
  application/
    app.go                   wiring: config, logger, database, migrations, HTTP server
    rest/                    handlers, DTOs, auth middleware, error responses
  config/                    environment-based configuration
  domain/
    entity/                  Company, User
    enum/                    company types
    errs/                    domain errors
    service/                 business logic: validation, PATCH, tokens
  infrastructure/
    persistence/             SQL queries and database error mapping
migrations/                  goose migrations, embedded into the binary
docs/                        generated Swagger spec
```

Dependencies point inwards: services depend on interfaces (`CompanySource`, `UserSource`), not on the database code,
and REST handlers depend on service interfaces.

## Development

```bash
make lint                          # golangci-lint
make test-integration              # HTTP + Postgres via testcontainers; requires Docker
make goose-create name=add_index   # new migration in ./migrations
```

Integration tests start a disposable Postgres 17 container, apply goose migrations and hit the real chi router.

Migrations are applied automatically when the service starts.

## Authentication: simplifications

Authentication is intentionally minimal. It covers the requirement that only authenticated users can mutate data, but
it is not a complete identity system:

- **No registration or user management.** There is a single test user created by a migration. Tokens can only be
  obtained through `/auth/v1/login`.
- **Simple password hashing.** Passwords are hashed with SHA-1 and a static salt from the environment. A real system
  should use bcrypt or argon2 with a per-user salt.
- **Shared secret.** Tokens are signed with HS256, so every service that verifies tokens needs the same secret.
  Asymmetric keys (RS256 / EdDSA) or an external identity provider would be the next step.
- **No refresh tokens and no revocation.** A token stays valid until it expires (`AUTH_TOKEN_TTL`).
- **No roles or permissions.** Any authenticated user can create, update and delete any company.
